# Рабочий алгоритм AgentYard

Четыре части, которые работают вместе:

1. **Матрёшечная декомпозиция** — задача дробится до атомов, а принятые решения передаются вниз, вбок и вверх.
2. **Классификатор пулов** — одинаковые задачи объединяются, решение принимается один раз.
3. **Строгий конвейер** — задачи идут по очереди и доделываются, а не перемешиваются.
4. **Подробные шаги** — у атомарной задачи есть пошаговая инструкция и признаки готовности, которые проверяет программа.

Ниже для каждой части: зачем она нужна, по шагам что делает программа и где это в коде.

Под этими частями работает движок оркестрации: проверки по частям проекта, сравнение с исходным состоянием, разбор неудач, политика следующего шага и цена смен моделей. Он описан в [ENGINE.md](ENGINE.md).

## Откуда взялся алгоритм

- Диспетчер каждый раз брал «самую выгодную» пару задача+модель. В итоге 16 задач перемешивались, начатые бросались ради новых, модели менялись туда-сюда (ревью делает другая модель).
- Ревьюеры смотрели только diff и возвращали правильные задачи: «нет импорта Table» (импорт был, проверка типов прошла) и «другие страницы не изменены» (их делают другие задачи).
- Атом T2.p3 получал бриф «ещё 2 файл(а)» и правил один файл из двух.

## 1. Матрёшка: дробление до атома и передача решений

**Атом** — задача, которую маленькая модель делает за один ответ: один файл (или файл и его стили), одно действие, с шагами и проверяемым критерием.

Дробление ленивое: программа не дробит заранее то, что может получиться целиком.

1. План даёт задачи верхнего уровня. Корень матрёшки — сама цель; её «сборка» — приёмка по цели.
2. Задача не выходит (лестница: повтор → аналитик → дробление → старшая модель → другой подход) — планировщик делит её на части.
3. Задача **не исчезает**: она становится составной (`children`), а части получают `parent` и встают в очередь на её место (`seq` родителя + номер части). Кто ждал задачу, ждёт её сборки.
4. Перед дроблением планировщик получает принятые решения (см. ниже) и требование: части — атомы, у каждой поле `steps` (3–7 шагов).
5. Часть тоже может не выйти и раздробиться дальше (глубина ограничена: `ESCALATION.maxSplitDepth`).
6. **Сборка (подъём вверх).** Когда все части сделаны, программа проверяет критерий самой задачи на ветке сборки: её тесты, команды и признаки готовности.
   - Прошло: задача считается сделанной, её решение — объединение решений частей.
   - Не прошло: добавляется одна часть «довести до критерия» с текстом ошибки. Если не прошло и после неё — задача уходит к человеку.
   - Часть у человека: составная задача тоже уходит к человеку («не собрана: часть X ждёт человека»). Когда человек доделает часть, задача сама вернётся к агентам.

**Журнал решений** (`src/decisions.ts`). После каждого слияния программа записывает факты из diff, а не со слов модели:

- созданные и удалённые файлы, что из них экспортируется;
- добавленные и убранные импорты (одинаковые склеиваются: «в 5 файлах»);
- новые и исчезнувшие теги и CSS-классы, новые CSS-правила;
- поставленные пакеты;
- заметка исполнителя.

Куда идут решения:

- **вниз** — частям видны решения предков и того, от чего зависят предки;
- **вбок** — соседним частям, задачам того же пула, зависимым задачам и задачам с общими файлами;
- **вверх** — при сборке решения частей становятся решением родителя; приёмка по цели видит последние решения;
- **«как починили»** — задача, справившаяся с ошибкой, оставляет рецепт тем, кто падает на той же ошибке. Ошибки сравниваются по подписи без путей и чисел.

В запросе исполнителя это разделы «Место задачи в общей работе» (чья это часть, кто делает остальное) и «Уже принятые решения». Ревьюер получает раздел «Место задачи» и правило: не требовать правок в чужих файлах.

## 2. Классификатор пулов: одно решение на все одинаковые задачи

**Классификатор** (`src/pools.ts`) работает без модели:

1. Берёт не начатые задачи-правки с 1–3 файлами.
2. Сравнивает пути. Два пути — один шаблон, если отличаются только именем сущности, одинаковым во всех частях пути: `src/pages/address-list/ui/AddressListPage.tsx` и `…/audit-log-list/ui/AuditLogListPage.tsx` → `src/pages/*-list/ui/*ListPage.tsx`. Разный вид файла (list и edit) — не шаблон.
3. Сравнивает слова задачи без имён сущностей, путей и чисел (Жаккар ≥ 0.5).
4. Задачи, которые зависят друг от друга, в один пул не попадают: это цепочка, а не повтор.
5. Первый в очереди член пула — **образец**. Остальные ждут его слияния (зависимость от образца).

Классификатор запускается после плана, после доработки по приёмке и после дробления.

Отдельно — **правка по образцу** (`similar`): план сам говорит «одна правка во всех файлах шаблона». Это тоже пул.

**Общее решение** (`src/rules.ts`) — правила, выведенные из правки образца:

1. Берутся тексты файла образца до и после слияния. Неважно, прислала модель фрагменты или файл целиком.
2. Построчное сравнение → блоки изменений → пары «старая строка ↔ новая» по похожести.
3. Внутри пары — сравнение по словам. Каждое отличие — правило замены с соседями слева и справа, например `<tr>` → `<Table.Tr>`, `<h1>` → `<h1 className="title">`. Слишком общее правило («(» → «[») заменяется правилом на всю строку.
4. Новые строки: импорт — после соседнего импорта (или после последнего), директива `'use client'` — в начало, остальное — после строки-соседа. Удалённые строки — правила удаления.
5. **Проверка:** правила, применённые к старому тексту образца, должны дать его новый текст. Не дают — программа их вслепую не применяет, только пишет по ним шаги для модели.
6. Из правил получаются **признаки готовности**: что исчезло из образца (теги `<table`, `<td`, класс `af-table`) не должно остаться в файле; что появилось (импорт `Table`) должно быть.

**Повтор решения** — после слияния образца, под замком слияния:

1. Для каждой не начатой задачи пула (или файла шаблона) правила применяются с подстановкой имени сущности (`address` → `order`, `Addresses` → `Orders`).
2. Результат по файлу:
   - **подошёл** — всё заменилось, старого не осталось, вставки встали;
   - **менять нечего** — нет ни мест из правил, ни следов старого;
   - **не подошёл** — например, `<td className="num">`, которого не было в образце, или похожая, но другая строка.
3. Подошедшие файлы проходят общие проверки (синтаксис, линтер, типы, тесты). Если ошибка указывает на конкретные файлы, откатываются только они, остальное проверяется ещё раз.
4. Каждая задача пула получает свой коммит (откат и поиск виновного остаются точными) и закрывается программой. Модель не вызывается.
5. Не подошедшие уходят к модели атомами (один файл), уже с решением-образцом (diff), шагами и признаками готовности. Ревью им не нужно: решение прошло ревью на образце, признаки готовности и проверки программа проверила. Это экономит смену модели.
6. **Снежный ком:** каждый сделанный атом учит программу. Его правка тоже становится решением, и программа пробует его на оставшихся не начатых задачах пула.
7. **Смена образца:** образец ушёл к человеку → образцом становится следующая задача пула, с пометкой, на чём упал прежний. Если не вышел и второй — остальные не начинаются: та же правка, скорее всего, не выйдет и у них. Человек делает образец руками → программа повторяет его в остальных.

Дублей больше нет. Остаток создаётся один раз, после слияния образца, а не на каждой переделке. Файлы, у которых уже есть задача пула, пропускаются.

## 3. Строгий конвейер и эпохи моделей

`src/conveyor.ts`. Смена модели в видеокарте — самое дорогое действие: 8–20 с, а при сбоящей видеокарте — риск сбоя. Раньше почти каждая задача платила за две смены: код одной моделью, ревью другой. Поэтому работа идёт **эпохами**, как цикл событий в движке JS:

- **Макрозадача** — загрузить модель. Грузится модель, у которой больше всего работы: сумма весов её шагов и того, что они разблокируют, с поправкой на время загрузки.
- **Микрозадачи** — всё, что загруженная модель может сделать, пока она в памяти. Порядок:
  1. ревью, которое она может сделать;
  2. начатое — переделка, разбор аналитиком, дробление, «старшая» модель;
  3. новые задачи по очереди `seq`, пока в работе меньше 3 (WIP);
  4. ещё независимые задачи сверх WIP (до 6), если иначе пришлось бы менять модель.
- **Между микрозадачами** процессорная дорожка доделывает проверки и слияния. Если у модели работы нет, но идут проверки, конвейер ждёт их (секунды): после проверок работа для неё может появиться (переделка). Модель меняется только когда её очередь пуста и ждать нечего.

Правила выбора:

- **Сродство с загруженной моделью.** Она берёт шаг, если её оценка (успех × вес ÷ (время + смена)) не хуже 60% от лучшей модели.
- **Ревью той же моделью** — для маленькой правки одного файла, которую уже проверила программа (синтаксис, типы, признаки готовности).
- **Ревью другой моделью** («вторая пара глаз») — для образцов пула, правок по шаблону, тестов, задач покрупнее и правок в нескольких файлах. Такие ревью копятся и делаются пачкой после смены модели.
- **Ревью образца, которого ждут другие задачи** (≥ 2), — сразу после начатой работы текущей модели, даже ценой смены.

Порядок задач прежний: части задачи — на её месте, задачи пула — за образцом, начатое доделывается раньше нового. Пока программа повторяет решение в задачах пула, модели эти задачи не берут.

Замер на прогоне 20261020100147:

- 16 смен ≈ 3,5 мин из 41 мин;
- планировщик при дроблении думал ≈ 9 мин — теперь он рассуждает коротко.

В учебном прогоне из 6 независимых задач, где нужно ревью другой моделью, теперь 3 смены вместо 6–8.

## 4. Подробные шаги и признаки готовности

У атома есть:

- **`steps`** — шаги. Для задач пула их пишет программа из правил, например:
  1. Открой `src/pages/user-list/ui/UserListPage.tsx` — правь только его.
  2. Если такого импорта ещё нет — добавь после последнего import: `import { Table } from '@mantine/core'`.
  3. Каждое `<table className="af-table">` замени на `<Table striped highlightOnHover withTableBorder>`.
  4. Каждое `<tr>` замени на `<Table.Tr>` …
  5. Программа не смогла заменить сама: в файле есть варианты, которых не было в образце (`<td`). Поменяй их по тому же принципу.
  6. Проверь себя: в файле не должно остаться `<table`, `<td`, `af-table`; должно быть `import { Table } …`.

  Для задач из плана и дробления шаги пишет планировщик (поле `steps` в схеме плана).
- **`doneWhen`** — признаки готовности. Программа проверяет их на ступени 2 каскада («признаки готовности»), до синтаксиса и типов. Пропущенное место ловится сразу и с точным текстом («ещё осталось `<td` — замени так же, как в образце»), а не через ревьюера.
- **Решение-образец** — diff принятой правки, показывается исполнителю.

## Копилка решений (skills/learned)

Задача упала на проверке (синтаксис, линтер, типы, тесты), а потом прошла — у агента или у человека. Тогда программа записывает решение в `skills/learned/<раздел>.md`. Разделы: типы и сборка, линтер, синтаксис, тесты, пакеты и зависимости.

Что входит в запись:

- **ошибка** без путей проекта;
- **теги**:
  - код ошибки (`ts2322`, `eresolve`);
  - имена из ошибки (`colorscheme`);
  - библиотеки с мажорной версией (`mantine`, `mantine@9`);
  - язык файла;
- **что помогло**: заметка исполнителя и факты по diff;
- **кусок правки** рядом с именами из ошибки;
- **ссылки**, если справку искали в интернете;
- **счётчик повторов.**

Та же ошибка второй раз не дублируется: увеличивается счётчик.

Где копилка проверяется:

- **При первой же ошибке проверок** — раньше справки по типам библиотек и поиска в интернете. Без сети и без ожидания. Совпадение оценивается по коду ошибки, именам, библиотекам и похожести текста. В запрос исполнителя идут только уверенные совпадения.
- **При планировании.** Записи по библиотекам проекта и словам цели идут планировщику как «подводные камни».

Файлы — обычный Markdown, их можно читать, править руками и отдавать коллегам. На учебной модели копилка только в памяти, чтобы не засорять её.

## Проверка причин ревью фактами

Перед возвратом задачи программа проверяет причины ревьюера (`vetReview`):

- **«нет импорта X» / «X не определён»** — если X используется и импортирован (или объявлен) во всех изменённых файлах, где используется, причина снимается. Если в проекте есть проверка типов и она прошла, это тоже указывается.
- **«другие страницы не изменены»** у задачи-части (пул, матрёшка, правка по образцу) — снимается: это работа других задач или программы.

Сняты все причины — задача принята. В журнале видно, какие причины сняты и почему.

Ревьюер теперь получает:

- раздел «Уже проверено программой» (проверки пройдены, признаки готовности выполнены);
- небольшие изменённые файлы целиком (видны импорты вне diff);
- указание оценивать только свою часть.

## Критерий не падает на старых ошибках проекта

Прогон 20261020112744 застрял из-за критерия. Планировщик вписал в критерий задач `npx --no-install tsc --noEmit`. Эта команда падала на двух старых ошибках чужих форм (AuditLogForm, PidorushkyForm). Исполнители и аналитик стали чинить эти формы вместо своей задачи, а задачи дробились снова и снова.

Что сделано:

- **Дубли проверки типов и линтера** (`tsc`, `eslint`, `npm run typecheck|lint` или команда проекта) убираются из критерия:
  - при проверке плана;
  - перед работой, если задача пришла из старого плана.

  Проверка типов и так идёт отдельной ступенью. Ошибки, которые были до прогона, там не считаются.
- **Любая команда критерия** (ступень «команды», сборка составной задачи, проверка «менять нечего») не считается проваленной, если падает только на ошибках, которые были до прогона.
- **Тормоз дробления.** Задача не дробится без конца: на большой глубине программа ищет справку по ошибке, а не делит задачу ещё раз.

## «Стоп»

Раньше «Стоп» был мягким: текущий запрос к модели дорабатывал до конца. Приёмка или длинное рассуждение — это до 45 минут, и кнопка как будто не работала.

Теперь запрос к модели (и загрузка модели) обрывается сразу:

- задача, чей запрос оборван, возвращается к состоянию до этого шага, попытка не засчитывается;
- идущие проверки доделываются;
- остальное уходит человеку с причиной «прогон остановлен человеком»;
- «Продолжить прогон» продолжает с того же места.

В окне кнопка становится «Останавливаю…», а в строке состояния видно, что именно сейчас обрывается.

## Справка из интернета

- Ссылки Bing приходят через переход `bing.com/ck/a?…u=a1<base64>`. Программа раскрывает их в настоящий адрес, иначе страницы не читались: 6 ссылок, 0 выдержек.
- Ссылки не по делу отсекаются. Ссылка остаётся, только если в ней есть код ошибки или хотя бы два значимых слова из запроса.
- Наши собственные проверки («признаки готовности», «фрагмент не найден») в интернете не ищутся.
- Библиотека добавляется в запрос, даже если её нет в тексте ошибки. Сначала программа ищет пакет, где объявлен тип из ошибки. Если его нет — пакет, чей вызов стоит в строке с ошибкой (`form.setValue` → `form = useForm()` → `react-hook-form`). Без этого находились только общие статьи про TS2345.
- Найденная справка видна в панели задачи вместе со ссылками, а во время поиска в строке состояния видно, что ищется и какие страницы читаются.
- Ответ gpt-oss, который Ollama не смогла разобрать как вызов инструмента (`error parsing tool call`), больше не теряется. Программа достаёт из ошибки сырой JSON и закрывает скобки. Раньше на этом пропадали попытки.

## Что видно в окне
