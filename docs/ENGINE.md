# Движок оркестрации

Движок решает четыре вопроса:

1. какой шаг делать следующим и какой моделью — с учётом того, что смена модели стоит 7–20 секунд;
2. чем проверять шаг;
3. чья неудача, если шаг не прошёл проверки;
4. что делать после неудачи.

Код лежит в `src/engine/` и `src/conveyor.ts`; связывает всё `src/pipeline.ts`.

## Почему понадобился

Прогон 20261020144005 («Тест мусор»: backend на Go + web на Next). Цель — Mantine, таблицы из кита и красивая шапка.

- Задачу про `web/app/layout.tsx` проверял `go test` бэкенда. Он был красным ещё до прогона: в проекте нет `go.sum`.
- Кодер с первой попытки сделал верную правку. Её отклонили 5 раз подряд: два кодера, аналитик, дробление и «старшая» модель.
- Дробление добавило тест `tests/layout-mantine-provider.test.tsx` в корень проекта. Запустить его там нечем. Его «красноту» тоже проверял `go test`, поэтому проверка «прошла».
- Пакет `@mantine/core` никто не ставил. Ставить его было некуда: в корне нет `package.json`.
- Итог: простейшая задача ушла человеку, а следом за ней — все зависимые.

## 1. Части проекта (`engine/workspace.ts`)

Проект может состоять из частей: `backend/` на Go, `web/` на Node. Каждая задача проверяется командами только той части, где лежат её файлы.

| Что | Как |
|---|---|
| Проверка типов, линтер, тесты | Команды частей, которым принадлежат файлы задачи. Файлы вне частей (README в корне) проверяются синтаксисом, признаками готовности и ревью. |
| Тесты задачи | Запускает раннер её части, пути — от папки части. Если у части нет раннера, тесты у задачи убираются ещё в плане. В бриф добавляется «Тестов не писать». |
| Пакеты npm | Ставятся в папку node-части (`web/`). В ветке прогона дописываются в `web/package.json`. |
| Ссылки на `node_modules`, `.venv` | Создаются в рабочих копиях для каждой части. В коммиты не попадают. |
| После установки | Команды части определяются заново: в `node_modules` появился `tsc`, и у web теперь есть проверка типов. |

## 2. Сравнение с исходным состоянием (`engine/baseline.ts`)

Задача отвечает только за новые падения.

Если команда проверки упала, программа один раз запускает ту же команду на исходном состоянии прогона: ветке до первой задачи, в отдельной рабочей копии. Результат запоминается. Затем падения сравниваются как «мешки» ключей:

- ошибки компилятора и линтера: файл + код ошибки, без номеров строк;
- упавшие тесты: Go (`--- FAIL`, `FAIL пакет`), node:test, jest/vitest, pytest;
- проблемы окружения: нет `go.sum`, нет модуля Python, нет скрипта npm.

Пути рабочих копий, время и числа из сравнения убираются. Если у вывода нет узнаваемых ключей, сравнивается подпись: первые строки вывода.

Правила:

- **Падает только то, что падало и до прогона** — ступень пройдена. В журнал один раз пишется «падает так же, как до прогона».
- **Появились новые падения** — исполнитель видит именно их, отдельно от старых.
- **Команда запускает ровно тесты задачи** (шаблон с файлами) — сравнения нет: починить этот тест и есть задача.
- **Полный набор тестов в конце** проверяется так же. Красный, как до прогона, — значит, «задачи нового не сломали». Если появились новые падения, виновный коммит ищется bisect'ом. «Хороший» коммит — тот, где нет новых падений.

## 3. Разбор неудачи (`engine/triage.ts`)

Прежде чем подниматься по лестнице, программа определяет класс неудачи.

| Класс | Как узнаётся |
|---|---|
| ошибка модели (`own`) | ошибка в файлах задачи |
| задела другие файлы (`collateral`) | ошибка называет только чужие файлы |
| окружение (`environment`) | не найден пакет (`TS2307`, `Can't resolve`), нет утилиты, нет `go.sum`, нет модуля Python, нет сети |
| формат (`format`) | ответ модели не по формату |
| сбой модели (`infra`) | тайм-аут, обрыв, Ollama не ответила |
| ревью, конфликт | по подписи |

Кроме разбора после неудачи, программа проверяет импорты сразу после правки. Если изменённый файл импортирует пакет, которого нет в `package.json` его части, программа ставит пакет до проверок. Модель тут ни при чём, попытка не тратится.

## 4. Что делать после неудачи (`engine/policy.ts`)

| Неудача | Что делает программа |
|---|---|
| Нет пакета | Ставит его и запускает задачу снова. Попытка не тратится. Если установка запрещена — передаёт человеку и пишет команду `npm install …`. |
| Сеть, утилита, `go.sum` | Один повтор без траты попытки, потом человек с точной причиной: «мешает окружение, а не код». |
| Сбой модели | Повтор без траты попытки. Во второй раз — другая модель. С третьего раза — человек: «проверь Ollama». |
| Формат | Напоминает формат. Если та же модель ошиблась второй раз — берёт другую модель. |
| Прогресс: упала на более поздней проверке или ошибок стало меньше | Та же ступень, без аналитика и дробления. Бюджет — до +2 попыток. |
| Та же правка второй раз | Модель зациклилась: сразу аналитик, дальше — выше по лестнице. |
| Та же ошибка второй раз | Ступенью выше. |
| Иначе | Повтор с текстом ошибки. |

В статистику успехов моделей идут только неудачи самой модели: `own`, `collateral`, `format`. Окружение, сбои Ollama и старые падения проекта не считаются.

Статистика хранится «окном» примерно из 20 последних задач. Старые неудачи из прогонов со сломанными проверками больше не держат модель внизу.

## 5. Планировщик со сменами моделей (`engine/scheduler.ts`, `conveyor.ts`)

Видеокарта держит одну модель, а смена стоит 7–20 секунд. Поэтому выбор модели для шага и решение о смене считаются в одних единицах — **ожидаемых секундах до успеха**:

```
ett(m, шаг) = смена(m) / n  +  τ(m) / p(m)  +  (1 − p(m)) · 60 с
```

Что здесь что:

- **смена / n** — цену загрузки модели делят все n шагов, которые она может сделать за одну загрузку. Пачка дешевле одиночки.
- **τ / p** — ожидаемое время до успеха с учётом повторов.
- **(1 − p) · 60 с** — сколько стоит неудача сверх самого повтора: проверки, ступень лестницы.
- **p** — успех модели на этой роли. Если эта же модель уже не справилась с задачей, её p для этой задачи снижается.

Правила:

- **Загруженная модель оставляет шаг себе**, если её ett не хуже лучшей модели плюс половина цены смены. Уйти и вернуться — это две смены. Слабая модель (p = 0.16) больше не держит задачу только потому, что уже в памяти: 6 / 0.16 + 0.84 · 60 = 88 с против 17 + 10 / 0.6 + 0.4 · 60 = 58 с у сильной.
- **Эпоха.** Пока модель в памяти, она делает всё, что может: ревью, начатое, новое по очереди. Если иначе пришлось бы менять модель, она берёт и независимые задачи сверх обычного предела (до 6 в работе). Если её работа кончилась, но идут проверки, программа ждёт их, а не меняет модель.
- **Следующая модель** выбирается по производительности эпохи: Σ вес · p / (смена + Σ τ).
- **Срочное ревью** (образец пула, которого ждут ≥ 2 задачи) прерывает эпоху только при условии: `ждущих · сколько ещё работать загруженной > смена туда + смена обратно`.
- **Своё ревью.** Маленькую проверенную программой правку ревьюит та же модель. Общий файл стилей рядом с правкой не делает её «крупной».
- **План** составляет модель, которая уже в памяти, если она планирует почти так же хорошо (не хуже лучшей на 0.1).

## 6. Несколько вариантов правки на повторе (`pipeline.ts`, `SAMPLING` в `config.ts`)

Подход взят из Agentless: модель предлагает несколько кандидатов, а программа проверяет их и берёт прошедший. После собственной ошибки модели (не окружения) исполнитель даёт ещё два ответа с другой температурой (0.55 и 0.85). Это та же модель, без смены. Программа проверяет варианты по очереди и берёт первый прошедший. Если не прошёл ни один, дальше по лестнице идёт ошибка лучшего: того, что упал позже всех и с меньшим числом ошибок. Маленькая модель часто попадает со второго-третьего ответа, а не с пятой попытки по лестнице.

## 7. «На чём споткнулись» и подсказка человека (`engine/stumble.ts`)

У задачи, которая уже не прошла хотя бы раз, в панели есть блок «На чём споткнулись»:

- ступень, на которой остановились: проверка типов, тесты, ревью, признаки готовности;
- ошибки с местом: файл и строка, без путей рабочих копий;
- что пробовали: попытки по моделям и классам неудачи;
- что именно нужно от человека.

Под блоком — поле для решения: кусок кода, правильный импорт или пара слов. Кнопка «Передать агентам с подсказкой» работает так:

- подсказка уходит исполнителю разделом «Подсказка человека» в каждой следующей попытке;
- попытки начинаются с нуля, задача не дробится;
- если задача составная, подсказка уходит её застрявшей части;
- если прогон уже закончился, он продолжается.

Если прошла задача, которая до этого падала, решение попадает в копилку решений. Так одна подсказка помогает и в следующих прогонах.

## 8. Задачи не про код (`engine/extract.ts`)

Цель может быть такой: «краткое содержание договора», «вытащи заказы из выгрузки в таблицу», «переведи csv в json». Тогда:

- у задачи есть `inputs` — исходные файлы. Программа сама извлекает из них текст, без внешних библиотек: docx, odt, xlsx (листы через `;`), pptx, html, rtf, csv, json, txt. PDF — по возможности: из скана или PDF со сложными шрифтами текст не достать, и программа так и говорит;
- результат — новый файл в `out/`. Проверка — сам результат: файл не пустой, JSON разбирается, в CSV у всех строк одно число колонок. Тест для такой задачи не нужен;
- большой документ, который не влезает в запрос, программа режет по абзацам. Каждая часть — отдельная задача «выпиши всё нужное для итога» (выжимки в `out/.parts/`). Последняя задача собирает итог из выжимок. Если и выжимки большие, итог режется снова;
- задачи над документами не объединяются в пулы: у каждой свой текст;
- папка без кода — нормальный случай: git-репозиторий программа создаёт сама.

## 9. Понятный план: этапы и без дублей (`plan.ts`)

- **Этапы.** У каждой задачи есть `stage` — короткое название шага цели: «Подключить UI-кит», «Таблицы из кита», «Шапка кнопками». На доске видны этапы-станции на одном пути, под каждым — его задачи с номерами 1.1, 1.2. Части задачи вложены под ней (2.1.1, 2.1.2). Повторы решения образца свёрнуты в одну строку: «Повтор решения ещё в 14 файлах — готово 12». Доделки после проверки итога и доработки по просьбе человека идут отдельными этапами.
- **Склейка дублей.** Две задачи одного типа с теми же файлами и почти тем же названием или брифом — это одна задача. Например, «Подключить MantineProvider в layout» и «Подключение MantineProvider к layout». Зависимости переписываются на оставшуюся задачу. Одинаковая правка в разных файлах дублем не считается: её объединяет классификатор пулов.

## Проверка

- `test/engine.test.ts` проверяет каждый модуль движка по отдельности: части проекта, сравнение с исходным состоянием на настоящем выводе `go test` из прогона, разбор неудач, политику, цену смен.
- `test/monorepo-e2e.test.ts` повторяет прогон 20261020144005. Проект — backend с красными до прогона тестами (настоящий Go, если он установлен) и web без тестов и без `node_modules`. Тот же план, что тогда: тест в корне, пакеты не указаны. Результат: обе задачи сделаны с первого раза, без человека. Тест убран ещё в плане, `@mantine/core` поставлен в `web/` и дописан в `web/package.json`, бэкенд при проверке web-задач не запускался. Отдельный тест — задача бэкенда: красные до прогона тесты ей не засчитываются.
- `test/human-docs.test.ts` проверяет:
  - чтение docx, xlsx, html и pdf;
  - нарезку большого текста по абзацам;
  - проверку файла-результата;
  - блок «на чём споткнулись»;
  - склейку дублей;
  - краткое содержание docx в папке без кода;
  - большой документ по частям;
  - подсказку человека, которая доходит до исполнителя;
  - выбор прошедшего варианта правки.
- Тот же сценарий проверен на копии настоящего проекта: обе задачи сделаны с первого раза, смен моделей меньше вдвое (4 → 2).
